# تحليل ميزة Workflow Configuration وتوزيع المطالبات

## الهدف من المستند

توضيح كيف يمكن إضافة قواعد توزيع آلي للمطالبات على المستخدمين دون كسر آلية الإسناد الحالية، والإجابة عن ثلاثة أسئلة أساسية:

1. كيف يعمل النظام وقاعدة البيانات حاليًا، وما الحالات المناسبة لدخول المطالبة في التوزيع؟
2. ما تغييرات قاعدة البيانات والنظام المطلوبة، وكيف ستتم عملية اختيار المستخدم وأولوية القواعد؟
3. كيف نتعامل مع البيانات القديمة ونحافظ على الإسناد اليدوي؟

> **حدود التحليل:** تمت مراجعة أجزاء من `Claim` و`Assigning` و`AssigningService` و`ClaimStatus` و`Roles` في فرع `main`. التصميم أدناه مقترح. يجب تأكيد جميع مسارات الإسناد، وتعريف المطالبة النشطة، وقواعد العمل النهائية قبل التنفيذ. أسماء الجداول والأعمدة الجديدة مقترحة وليست Migration منفذة.

## 1. تحليل قاعدة البيانات والنظام الحالي

### 1.1 ما الموجود حاليًا؟

- جدول `claims` يمثل المطالبات، وحالة المطالبة موجودة في `status` وفق قيم `ClaimStatus`.
- جدول `assignings` يسجل تاريخ الإسناد. من الكود الحالي تظهر حقول مثل `claim_id` و`from` و`to` و`supervisor_id` و`assign_date` و`is_active`.
- العلاقة في `Claim` تعرض سجلات الإسناد عبر `assignees()`، والإسناد النشط عبر `assignee()` الذي يبحث عن `is_active = 1`.
- خدمة `AssigningService` الحالية توزّع قائمة مطالبات على المستخدمين المحددين، وتعطّل الإسنادات السابقة للمطالبات المختارة ثم تضيف سجلات إسناد جديدة. كما يوجد مسار إسناد جماعي من ملف Excel.
- المستخدم مرتبط بدور من خلال `users.role_id` وعلاقة `role()`، كما يوجد `supervisor_id` وعلاقة بالمستخدمين التابعين.
- توجد أدوار معرفة في `Roles` مثل `SUPERVISOR` و`COLLECTOR` و`SENIOR_COLLECTOR` وغيرها. يجب استخدام أدوار النظام الفعلية، لا إنشاء تعريف موازٍ للأدوار.

**النتيجة:** الأفضل أن يختار الـ Workflow المطالبات والمستلمين، ثم يمرر الإسناد إلى مسار إسناد مشترك يحافظ على سجل `assignings`. لا ننشئ جدولًا ثانيًا يصبح مصدرًا بديلًا للإسناد.

### 1.2 ما حالات المطالبات التي تدخل التوزيع؟

قيم `ClaimStatus` الحالية تشمل: `registered`، `assigned`، `rejected`، `approved`، `follow_up`، `follow_up/delay`، `follow_up/partial`، `law_firm`، `default_in_payment`، `default_in_payment_by_system`، `closed`، `done`، وحالات تحصيل أو إجراءات أخرى.

الحالة وحدها لا تكفي لتحديد قابلية التوزيع؛ يجب فحص حالة المطالبة **مع** سجل الإسناد النشط، لأن تاريخ الإسناد محفوظ في `assignings`.

| الحالة الحالية | التوصية المبدئية للتوزيع الآلي | السبب / الشرط |
|---|---|---|
| `registered` | **مؤهلة مبدئيًا** | تدخل التوزيع إذا لم يكن لها إسناد نشط وكانت مستوفية لشروط العميل والقاعدة. |
| `assigned` | **مستبعدة افتراضيًا** | لا نعيد إسنادها تلقائيًا إلا إذا فعّل المسؤول قاعدة إعادة توزيع واضحة. |
| `approved` | تحتاج قرارًا تجاريًا | لا نفترض أنها غير مسندة أو قابلة للتوزيع دون مراجعة دورة العمل الحالية. |
| `follow_up`، `follow_up/delay`، `follow_up/partial` | مستبعدة افتراضيًا | تبدو حالات متابعة؛ نقلها لمستخدم آخر يحتاج قاعدة صريحة لإعادة الإسناد. |
| `law_firm` | مستبعدة افتراضيًا | تحويل لمسار قانوني؛ لا يدخل توزيع المحصلين العام إلا إذا كان هناك Workflow مستقل لهذا المسار. |
| `rejected`، `closed`، `done`، وحالات التحصيل/الإغلاق | مستبعدة افتراضيًا | حالات نهائية أو تحصيلية غالبًا؛ يجب تأكيد التصنيف من قواعد العمل قبل التنفيذ. |
| `default_in_payment`، `default_in_payment_by_system` | مستبعدة من التوزيع العام افتراضيًا | حالات متابعة خاصة، ولا يعاد توزيعها إلا بقواعد محددة. |

**قاعدة V1 المقترحة:** ابدأ بالمطالبات ذات الحالة `registered` والتي **لا تملك إسنادًا نشطًا**. اجعل إعادة توزيع المطالبات المسندة خيارًا منفصلًا، مع شروط واضحة وتسجيل سبب النقل. لا تغيّر `claims.status` تلقائيًا إلا إذا كان ذلك جزءًا مؤكدًا من سلوك الإسناد الحالي.

يجب اعتماد قائمة الحالات النهائية مع مالك العملية؛ أسماء الحالات وحدها لا تثبت كل قواعد العمل.

## 2. التغييرات المطلوبة في النظام وقاعدة البيانات

### 2.1 تصميم قاعدة البيانات المقترح

هذه بنية منطقية أولية، وليست وصفًا للمخطط الحالي ولا Migration جاهزة.

#### `workflows` — تعريف قاعدة التوزيع

| الحقل المقترح | الغرض |
|---|---|
| `id` | المفتاح الأساسي |
| `name`، `description` | اسم القاعدة ووصفها |
| `is_enabled` | تفعيل/إيقاف التنفيذ |
| `priority` | أولوية الـ Workflow مقارنة بغيره |
| `schedule` أو إعدادات التشغيل | وقت/نمط التنفيذ |
| `created_by`، timestamps | المسؤول عن الإنشاء وتواريخ التعديل |

#### `workflow_groups` — مجموعات الشروط والتوزيع

| الحقل المقترح | الغرض |
|---|---|
| `id`، `workflow_id` | تعريف المجموعة وربطها بالـ Workflow |
| `name` | اسم المجموعة |
| `priority` | أولوية المجموعة عند تداخل الشروط |
| `match_mode` | مثل `all` أو `any` للشروط داخل المجموعة |
| `assignment_mode` | مثل `role` أو `specific_users` |
| `role_id` | الدور المستهدف إذا كان الاختيار حسب الدور |
| `is_enabled` | إتاحة المجموعة |

#### `workflow_conditions` — شروط اختيار المطالبة

| الحقل المقترح | الغرض |
|---|---|
| `id`، `workflow_group_id` | ربط الشرط بالمجموعة |
| `field_key` | حقل مسموح من قائمة معتمدة |
| `operator` | عامل مقارنة مسموح |
| `value` | قيمة الشرط وفق نوع الحقل |
| `sort_order` | ترتيب العرض/التقييم عند الحاجة |

لا يُسمح بتخزين SQL حر أو تنفيذه من إعدادات المستخدم. الحقول والعوامل المتاحة يجب أن تكون قائمة آمنة يحددها المطور.

#### `workflow_group_users` — اختياري للمستلمين المحددين

يستخدم عند اختيار مستخدمين بعينهم بدلًا من الدور، ويربط المجموعة بالمستخدمين المختارين. يمكن اعتماد تصميم آخر إذا كانت هناك آلية موجودة مناسبة.

#### `workflow_runs` — سجل كل عملية تشغيل

يحتوي مبدئيًا على `id`، و`workflow_id`، ووقت البداية والنهاية، وحالة التشغيل، وملخص أعداد المطالبات، ومعرّف التشغيل/مفتاح منع التكرار.

#### `workflow_execution_logs` — نتيجة كل مطالبة

يحتوي مبدئيًا على `workflow_run_id`، و`claim_id`، والمجموعة التي طابقت المطالبة، والمستخدم المرشح/المختار، والنتيجة (`assigned` أو `skipped` أو `failed` أو `conflict`)، والسبب. يجب ألا يُنشأ سجل تاريخي مزيف لعمليات حصلت قبل إطلاق الميزة.

#### `workflow_audits` — تدقيق إعدادات القواعد

يسجل من غيّر الإعدادات، وما الذي تغير، ومتى.

**العلاقات الأساسية:**
- Workflow واحد ← مجموعات متعددة.
- المجموعة الواحدة ← شروط متعددة.
- المجموعة الواحدة ← دور مستهدف أو مستخدمون محددون حسب `assignment_mode`.
- Workflow واحد ← عمليات تشغيل متعددة.
- عملية تشغيل واحدة ← نتائج متعددة للمطالبات.
- كل إسناد ناجح يستمر في استخدام `assignings` كسجل الإسناد الفعلي.

لا تضف جداول للسعة/الـ Capacity قبل التأكد من عدم وجود مصدر موثوق قائم في النظام. كذلك يجب تأكيد أنواع الحقول والمفاتيح والفهارس من الـ migrations الفعلية قبل اعتماد المخطط.

### 2.2 كيف تتم عملية توزيع المطالبات على المستخدمين؟

**التدفق المقترح:**

1. يحدد المسؤول الحالات والحقول والشروط، ويحدد هل المستلمون يتم اختيارهم حسب **Role** أم من قائمة **Users** محددة.
2. يحدد المسؤول أولوية الـ Workflow وأولوية كل مجموعة شروط.
3. عند التشغيل، يختار النظام المطالبات المسموح بها فقط، ثم يقيّم مجموعات الشروط.
4. إذا لم تنطبق أي مجموعة، تسجل المطالبة كـ `skipped` مع السبب.
5. إذا انطبقت مجموعة واحدة، يحدد النظام المستلم وفق وضع الإسناد:
   - **اختيار حسب Role:** يستخرج المستخدمين النشطين المؤهلين لهذا الدور وضمن النطاق الصحيح، ثم يطبق سياسة التوزيع والـ Capacity المعتمدة.
   - **اختيار مستخدم محدد يدويًا:** يلتزم بالمستخدم الذي اختاره المسؤول، ولا يمنع الإسناد لمجرد تجاوز Capacity الخاصة بالتوزيع الآلي.
6. قبل الحفظ، يعيد النظام التحقق من صلاحية المطالبة والمستخدم والسعة عند انطباقها، ويمنع التكرار والتزامن غير الآمن.
7. يكتب الإسناد من خلال مسار الإسناد المشترك إلى `assignings`، ويسجل نتيجة التنفيذ.

#### ما معيار توزيع الحمل بين مستخدمي الدور؟

يجب تحديده كقرار عمل. الخيارات الممكنة:
- **Least-loaded:** اختيار المستخدم الأقل في عدد/وزن المطالبات النشطة.
- **Round-robin:** التناوب بين المستخدمين المؤهلين.
- **Capacity-aware:** استبعاد من وصل إلى الحد المحدد، ثم تطبيق معيار الاختيار على الباقين.

لا يمكن تحديد الصيغة الصحيحة للحمل قبل اعتماد تعريف «المطالبة النشطة»، وهل الحمل يُحسب بعدد المطالبات أم بقيم/أوزان مختلفة. يفضّل في V1 اختيار معيار واحد واضح، وتسجيل سبب اختيار كل مستخدم. لا تستخدم عدد سجلات `assignings` التاريخية كلها لحساب الحمل؛ يجب تحديد ما يدخل في الحمل الحالي، مثل الإسنادات النشطة فقط، وفق قرار العمل.

### 2.3 هل ستتأثر عملية Manual Assignment؟

هناك خياران، والتوصية هي الخيار الثاني:

- **الخيار A — فصل كامل:** تظل كل عمليات الـ Manual خارج منطق الـ Workflow والـ Capacity، ولا يتغير سلوكها الحالي.
- **الخيار B — تطبيق الحساب عند الاختيار حسب Role فقط (الموصى به):**
  - إذا اختار المسؤول Role ليقوم النظام بتحديد المستلم، يطبق النظام شروط الأهلية والتوزيع والـ Capacity.
  - إذا اختار المسؤول مستخدمًا بعينه أو مجموعة مستخدمين يدويًا، يتبع النظام الاختيار اليدوي ولا يمنعه لمجرد تجاوز Capacity الخاصة بالـ Workflow.
  - يظل التحقق من الصلاحيات وصحة المطالبة والمستخدم وسجل الإسناد مطلوبًا في الحالتين.

يجب التمييز بين **طريقة اختيار المستلم** وبين **مصدر العملية**. الأفضل تمرير سياق موثوق من جهة الخادم مثل `assignment_mode = role | specific_users` و`source = workflow | manual | import | transfer`. لا تعتمد على قيمة يرسلها العميل دون تحقق، ولا تستخدم تجاوزًا عامًا يعطّل بقية التحققات.

هذا الاختيار يحافظ على مرونة الـ Manual، وفي الوقت نفسه يسمح بتطبيق الحساب عندما يكون المطلوب أن يختار النظام المستخدمين بناءً على الدور.

### 2.4 ماذا يحدث إذا تحققت مجموعتا شروط في نفس الوقت؟

يجب أن تكون الأولوية قابلة للتحكم من المسؤول، لا أن تعتمد على ترتيب الاستعلام أو ترتيب السجلات.

**المقترح:**
1. يمنح المسؤول كل Workflow أولوية، وكل مجموعة أولوية داخل Workflow.
2. إذا طابقت المطالبة عدة مجموعات، يرتبها النظام حسب الأولوية المعتمدة (مثل الرقم الأقل أولًا أو الأعلى أولًا، لكن يجب تثبيت معنى الأرقام في الواجهة).
3. **الافتراضي: تُنفذ مجموعة واحدة فقط لكل مطالبة في عملية التشغيل**، ثم تُسجل المجموعات الأخرى كـ `not_selected_lower_priority`. هذا يمنع إنشاء إسنادين متنافسين للمطالبة نفسها.
4. إذا تساوت الأولوية وكانت المجموعتان تختاران مستلمين مختلفين، فلا يُترك القرار لترتيب التنفيذ؛ إما رفض حفظ إعداد متعارض، أو تسجيل `conflict` وطلب تعديل الأولوية. لا نختار فائزًا عشوائيًا.
5. إذا كان المطلوب مستقبلًا تنفيذ أكثر من مجموعة للمطالبة نفسها، فيجب تصميم ذلك كحالة مستقلة صريحة، لا كسلوك افتراضي.

مثال: المجموعة A أولويتها 1 وتُسند إلى Role المحصلين، والمجموعة B أولويتها 2 وتُسند إلى مستخدم محدد. إذا انطبقتا معًا، تفوز A وفق ترتيب الأولوية المعلن، وتُسجل B كغير مختارة. إذا تساوتا، تظهر حالة تعارض بدل إسناد المطالبة مرتين.

## 3. التعامل مع البيانات القديمة

1. **فحص قبل التغيير:** احصر المطالبات ذات الإسناد النشط، والسجلات المكررة أو غير المتسقة، والمستخدمين المحذوفين/غير النشطين، وجميع المسارات التي تنشئ إسنادًا.
2. **الحفاظ على التاريخ:** لا تعدّل سجلات `assignings` القديمة لمجرد إدخال Workflow، ولا تعِد كتابة `from` أو `to`، ولا تنشئ سجلات تشغيل قديمة وهمية.
3. **Migrations إضافية:** أضف جداول الميزة وفهارسها وصلاحياتها بشكل إضافي، وأبقِ التنفيذ الآلي متوقفًا بعد النشر الأول.
4. **لا إعادة إسناد تلقائية:** المطالبات المسندة حاليًا لا يعاد توزيعها عند تفعيل الميزة إلا إذا وافق مالك العمل على نطاق إعادة توزيع واضح.
5. **Dry Run:** شغّل القواعد على مجموعة محدودة دون حفظ إسنادات، واعرض المطالبات المختارة والمستبعدة، والمستخدم المتوقع، والسعة، وأولوية القاعدة وسبب النتيجة.
6. **تحديد بداية التشغيل:** حدد هل المعالجة تشمل المطالبات الجديدة فقط أو مجموعة تاريخية محددة. لا تعالج كل المطالبات القديمة تلقائيًا.
7. **تفعيل تدريجي:** ابدأ بـ Workflow واحد ونطاق صغير، وراجع النتائج وسجل الأخطاء قبل التوسع.
8. **تأجيل القيود الخطرة:** لا تضف قيدًا يفترض إسنادًا نشطًا واحدًا لكل مطالبة قبل فحص البيانات الحالية وكل مسارات الكتابة والتأكد من توافق القيد مع العمل.
9. **التراجع:** إيقاف الـ Workflow يمنع إسنادات آلية جديدة، لكنه لا يحذف الإسنادات التاريخية ولا يمسح سجل التدقيق.

## 4. تأثير الميزة على النظام

| الجزء | التأثير المتوقع | وسيلة تقليل المخاطر |
|---|---|---|
| `claims` | قراءة الحالة والحقول المستخدمة في الشروط؛ لا يلزم تغيير الحالة تلقائيًا دون قرار واضح | قائمة حقول مسموحة وقواعد حالات معتمدة |
| `assignings` | يظل سجل الإسناد الفعلي، وتضاف إليه إسنادات جديدة عبر المسار المشترك | الحفاظ على السجل التاريخي وإعادة التحقق قبل الكتابة |
| المستخدمون والأدوار | اختيار المستلمين بناءً على الدور أو المستخدمين المحددين | تحقق من الدور والنشاط والنطاق والصلاحيات |
| الـ Manual | قد يتأثر إذا طُبقت Capacity على كل الإسنادات | تطبيق الحساب عند الاختيار حسب Role فقط، أو استثناء الـ Manual بوضوح |
| الـ Imports / Transfers | قد تتغير نتائجها إذا أُدخلت تحت قواعد Capacity العامة | سياسة مستقلة لكل مصدر |
| الأداء | تقييم الشروط وحساب الحمل قد يزيد استعلامات قاعدة البيانات | استعلامات مجمعة، فهارس مناسبة، ومنع N+1 |
| التشغيل والدعم | الحاجة لمعرفة لماذا أُسندت أو تخطّت مطالبة | Run logs ونتيجة وسبب لكل مطالبة |
| الصلاحيات | إضافة إدارة القواعد وتشغيلها | صلاحيات منفصلة وتدقيق التغييرات |

## 5. قرارات مطلوبة قبل التنفيذ

- اعتماد قائمة حالات المطالبات المؤهلة للتوزيع، وتحديد هل `approved` أو حالات المتابعة تدخل في أي Workflow.
- تعريف «الإسناد النشط» ومصدر حساب الحمل والـ Capacity.
- اختيار معيار توزيع مستخدمي الدور: الأقل حملًا، أو التناوب، أو معيار معتمد آخر.
- اعتماد أن اختيار Role هو الذي يفعّل حساب التوزيع والـ Capacity، بينما الاختيار اليدوي لمستخدم محدد لا يُمنع بسببها.
- اعتماد معنى رقم الأولوية وقاعدة فض التعادل، والافتراضي أن مجموعة واحدة فقط تُنفذ لكل مطالبة في كل تشغيل.
- تحديد سياسة المطالبات المسندة سابقًا، والاستيراد، والنقل، وإعادة الإسناد.
- تحديد ما إذا كان أول تشغيل يشمل المطالبات الجديدة فقط أم نطاقًا تاريخيًا محددًا.

## التوصية النهائية

ابدأ بـ V1 محدودة: المطالبات `registered` التي لا تملك إسنادًا نشطًا، والتوزيع حسب Role مع سياسة حمل واضحة وCapacity عند الحاجة. اجعل اختيار مستخدم محدد يدويًا خارج حظر الـ Capacity، وأضف أولوية صريحة للمجموعات مع منع الإسناد المزدوج. احتفظ بجدول `assignings` الحالي كسجل الإسناد، واستخدم Dry Run وتفعيلًا تدريجيًا قبل الإنتاج.
